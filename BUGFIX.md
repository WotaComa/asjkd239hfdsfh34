# Bugfix Report

## 1. Critical Code Review

### 1.1. `float` нельзя использовать как надёжное денежное представление

`float` является бинарным floating-point типом. Многие десятичные значения не могут быть представлены им точно.

Можно использовать decimal тип в базе а на стороне php работать с Value Object.

- хранить деньги в минимальных единицах (`int`, например копейках);
- либо использовать decimal/bcmath-подход;

Например, вместо `100.00` можно работать с `10000` копеек.

### 1.2. Нет валидации входных данных

Необходимо определить бизнес-правила и валидировать входные данные. Метод принимает произвольные значения:

- отрицательную базовую цену;
- скидку больше 100%;
- отрицательный coupon amount;
- отрицательный VAT;
- VAT/скидку с неожиданными диапазонами.

### 1.3. Минимальный платёж и защита от отрицательных значений противоречат друг другу по смыслу

В коде видно, что условие `$currentPrice < 0` скорее никогда не выполнится, потому что `MIN_VALUE` не будет отрицательной

### 1.4. `MIN_VALUE` зашит в сервисе

`100.00` — бизнес-настройка, а не обязательно техническая константа класса. В production её разумнее получать из конфигурации/тарифа/правил billing или передавать через объект политики расчёта.

### 1.5. Метод смешивает бизнес-правила и техническую реализацию

Один метод одновременно:

- рассчитывает скидку;
- рассчитывает купон;
- рассчитывает VAT;
- применяет minimum charge;
- выполняет округление.

### 1.6. Нет объекта результата расчёта

Для billing полезно иметь не только финальную сумму, но и breakdown. Это важно для invoice, аудита, поддержки клиентов и расследования расхождений:

- базовая стоимость;
- скидка лояльности;
- скидка купона;
- количество таксы;
- VAT;
- минимальная стоимость;
- финальная стоимость.


### 1.7. Нет явной информации о валюте

`100.00` не понятно к какой валюте относится это число(USD, RUB, EUR, etc..).

### 1.8. Недостаточно тестов как части финансового кода

Минимальный набор тестов должен покрывать:

- обычный расчёт;
- loyalty discount;
- coupon;
- loyalty + coupon;
- VAT после скидок;
- сумму ниже minimum;
- отрицательную сумму после скидок;
- скидку 0% и 100%;
- VAT 0%;
- граничные значения;
- правила округления.

## 2. Архитектура для добавления новых скидок

Подход: **Strategy + pipeline из правил расчёта**.

Идея:

```text
BillingCalculator
    -> список CalculationRule / DiscountStrategy
        -> LoyaltyDiscountRule
        -> AnnualSubscriptionDiscountRule
        -> BloggerPromoRule
        -> SeasonalSaleRule
        -> CouponRule
    -> VatRule
    -> MinimumTransactionRule
    -> RoundingRule
```

Каждое правило отвечает только за свою операцию и получает объект контекста расчёта.

Условно:

```text
context = new PriceContext(basePrice, customer, subscription, coupon, ...);

foreach($rules => $rule) {
    context = $tule$.apply(context);
}

return context.result();
```

Для денежных операций лучше разделить правила по типам и явно задать порядок их выполнения. Например:

```text
base -> discounts -> coupon -> VAT -> minimum -> rouding
```

Новые скидки тогда добавляются как новые стратегии/правила, а основной calculator не меняется.
